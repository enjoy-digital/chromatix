# Simulation Performance Study

Goal: evaluate how to speed up the Verilator simulation (`chromatix_sim.py`) and where the time
really goes. Not implemented yet: results and options logged for later.

## Targets

The Game Boy runs at 59.73 fps (4.194304MHz / 70224 cycles per frame).

| Target            | fps  | vs today (1.74 fps) |
|-------------------|------|---------------------|
| Realtime (1x)     | 59.7 | x34                 |
| 0.25x             | 15   | x8.6                |
| 0.1x              | 6    | x3.4                |
| Today, `--pgo`    | 2.2  | -                   |

Realtime is out of reach for a cycle-level RTL simulation: the design runs at hClk = 16.78MHz,
simulated at ~570ns/cycle today (~17ns/cycle would be needed). Reasonable goal: ~0.1x (slow-motion
but playable, graphics/menus/inputs checks); beyond that, C++ models of the CPU/APU (no longer
testing the gateware) or the hardware itself (realtime, UVC capture, debug bridge).

## Method

`python3 chromatix_sim.py --rom tobudx.gb --frames 60 --bench` (single clock, no PGO unless noted),
user CPU time compared when the machine was loaded. Correctness: frames 0/60/120/180/240
(`--every 60 --buttons start@150+10`) compared to reference captures.

## Where the time goes

- The model is evaluated twice per hClk cycle (rising/falling edges); the LiteX sim framework is
  ~3% of the time.
- gprof: gbc_snd 21%, T80 microcode (`t80_mcode`) 20%, T80 8.5%, video 6%, gb 5%, sprites 3%.
- The costly blocks are the VHDL ones converted by GHDL (`ghdl --synth --out=verilog`), which
  outputs a synthesis netlist rather than behavioral Verilog:
  - `case` statements become long chains of `ir == constant` compares ORed together (T80
    microcode: 14k lines, ~2000 compares, ~350ns per standalone evaluation). Verilator can't turn
    them back into jump tables and re-evaluates them on every edge.
  - Clock enables become a mux after the logic (`q <= ce ? next : q`): all the next-state logic is
    computed on every edge, even with ce low. Behavioral `if (ce)` would let Verilator skip it.

## Results

| Experiment                                               | Speed           | Correct | Verdict       |
|----------------------------------------------------------|-----------------|---------|---------------|
| Baseline                                                 | 1.74 fps        | yes     | -             |
| `--pgo` (existing)                                       | +26%            | yes     | available     |
| T80 microcode as a lookup table                          | 2.29 fps (+32%) | yes     | to implement  |
| gbc_snd stubbed (silent, upper bound of a faster APU)    | 2.16 fps (+23%) | no audio| to implement  |
| Fast-forward clocking (hClk/2, speedcontrol FASTFORWARD) | 2.61 fps (+49%) | **no**  | needs work    |
| speedcontrol/video negedge moved to posedge              | ~+5%            | timing changed | no     |
| `-march=native`                                          | ~+3%            | yes     | negligible    |
| Verilator `--threads 2` / `4`                            | 2x / 4.6x slower| -       | dead end      |

Threads: evaluations are ~1us, thread synchronization costs more than the parallel work.

### T80 microcode lookup table (prototype validated)

- `T80_MCode` is a pure combinational function; its effective inputs are 19 bits: `iset`(2),
  `ir`(8), `mcycle`(3), flags Z (bit 7) and C (bit 4) only, `nmicycle`, `intcycle`, `xy_state`(2).
  Checked exhaustively: varying the 6 other flag bits gives 0 mismatches.
- Table generated by running the GHDL netlist itself through Verilator on all 512K inputs (~1s,
  72 output bits per entry, 17MB `$readmemh` file); the module is replaced by a table read. Exact
  by construction.
- Frames identical to the reference.
- Integration plan: in `convert_vhdl` (`chromatix/gateware/sim.py`), after the GHDL conversion,
  build a small Verilator harness on the `t80_mcode` netlist, generate the table and replace the
  module (regenerated automatically when the VHDL changes).

### gbc_snd

- Sequential, so no table. Proposed: a behavioral Verilog translation of `gbc_snd.vhd` (~1750
  lines, simulation only), proven equivalent to the GHDL netlist by lockstep co-simulation (both in
  one testbench, all outputs compared each cycle, random register traffic + audio-heavy ROMs).
- Up to +23% (stub upper bound), somewhat less with a real model. The same approach could apply
  to the T80 core (8.5%).
- A generic fix (moving enables before the logic in GHDL's netlist) would need a netlist rewriting
  pass; the yosys-ghdl plugin produces the same netlist.

### Fast-forward clocking

- Idea: `speedup=1` (speedcontrol FASTFORWARD: ce every 2 clk_sys) with hClk halved, `cart_act`
  tied low: same Game Boy speed, half the evaluations.
- Frames wrong (white screen after boot). First cause found: `cart.v` sequences the cartridge bus
  on a fixed 16 hClk count per M-cycle (8 in CGB double speed); with hClk halved, the write strobe
  (count 8) falls after the M-cycle end and MBC writes are lost. Forcing the 8-cycle schedule was
  not enough: other logic (DMA/HDMA, video, ...) also assumes 4 hClk per Game Boy cycle, to trace.

## Estimate

Baseline 1.74 fps -> microcode table + gbc_snd + `--pgo`: ~3.5 fps (~0.06x); with fast-forward
fixed: ~5-6 fps (~0.1x).
